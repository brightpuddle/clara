# Plan: After-the-Fact Visibility (Track I)

Source of truth for task status. Process: `AGENTS.md` "Development Process".
Roadmap: `docs/ROADMAP.md` (Track I; I0 is done as Track S, ADR 0012).
Legend: `[ ]` todo, `[~]` in progress, `[x]` done (short SHA).

## Problem

All visibility need is retrospective: *what did Clara do, and is it working as intended?*
`trigger_runs` and `tool_calls` record raw facts (stdout, stderr, tool JSON), but a person
cannot answer either question from them. Two things are missing:

1. **A statement of intent.** Nothing says what "working" means for a trigger, so nothing
   can be judged.
2. **A human-scale account.** Raw rows are not a summary.

## Principles

- Judge each trigger against *its own declared expectations*, not generic heuristics.
- Silence is a failure mode. A trigger that stopped firing must be as visible as one that errors.
- Receipts are written by the script that knows what it did; Clara adds mechanical facts.
- Output is prose and short tables a person reads in two minutes, in the places already read
  (terminal, Webex/Discord, the vault).
- No new frontend. Reuse the cockpit for drill-down.

## Design

### 1. Linked records (schema)
Add to `trigger_runs`: `event_id`, `parent_run_id`, `session_id`, `receipt` (JSON).
Persist the triggering event (id, type, source, trimmed data) so "why did this run" is
answerable. Add a `trace` view/query: event -> trigger -> run -> tool calls -> agent session.

### 2. Run receipts
A script ends by emitting one structured receipt, via a new builtin tool `run.report`
(uses `CLARA_RUN_ID`; works from Bun, Python, shell via `clara tool call`):

```json
{"outcome":"ok|partial|failed|noop",
 "summary":"Triaged 14 messages: 9 filed by rule, 3 by LLM, 2 left for review. 2 reminders created.",
 "counts":{"seen":14,"rule":9,"llm":3,"review":2,"reminders":2},
 "anomalies":["LLM fallback used 3 times (usual 0-1)"]}
```
If a script reports nothing, Clara synthesises a mechanical receipt: exit code, duration,
tool-call counts by name, tool errors. `noop` is a first-class outcome ("ran, nothing to do").

### 3. Declared expectations (trigger YAML)
An optional `expect` block per trigger, validated by `schemas/trigger.schema.json`:

```yaml
expect:
  max_silence: 90m        # schedule: alert if no run in this window
  max_duration: 60s
  outcomes: [ok, noop]    # anything else is flagged
  min_activity: {counts.seen: 0}   # optional sanity bounds on receipt counts
```
Workers: `max_restarts_per_day`. Event triggers: optional `max_silence` for sources that
should always be chatty (e.g. sensors).

### 4. Health judgement
`clara health [--since 24h]` evaluates every trigger against `expect` plus its own history
(median duration, usual error rate, usual counts). Verdicts: `healthy`, `degraded`
(slower, noisier, more fallbacks than usual), `failing`, `silent` (should have run, didn't),
`unknown` (no expectation yet). Each verdict carries the evidence in one line.

### 5. Surfaces
- **`clara report [--since 24h] [--trigger id]`** prints a grouped, prose-first report:
  needs-attention first, then everything else as one line per trigger, then detail on demand
  (`clara run show` gains receipt and the linked trace).
- **Daily "what Clara did" note** written to the vault (markdown). Readable on every device,
  searchable, and a source for the memory spike (Track H).
- **Digest and alert** to `#notify`/Webex: the same note's headline plus any non-healthy
  trigger, once a day; immediate message only for `failing` and `silent`.
- **Cockpit "Runs" tab** (later): timeline, filter by verdict, drill into a run. Reuses
  the cockpit components.

## Version control for workflows (prerequisite for receipts)

Receipts require editing the live scripts, which currently have no version control
(roadmap A5). Decision needed as an ADR; recommendation:

- **Separate git repo `~/src/clara-workflows`**, independent of the clara repo and of chezmoi.
  Holds `scripts/`, `triggers/` (+`triggers-available/`), `mail_rules.yaml`, `theme.yaml`,
  schemas pointers, and its own `package.json`/lockfiles/tests.
- `~/.config/clara/{scripts,triggers,triggers-available}` become symlinks into it. Clara's
  `task_dirs` config could point at it directly instead.
- **Not in the repo:** `config.yaml` (holds secrets), `audit.db`, `certs/`, `backup*`,
  `sync-conflict*`, `node_modules`, `*.bak`, `sdk/clara.d.ts` (generated by `clara types gen`).
- `learned_rules.yaml` is machine-written state: keep out of the repo, or commit it
  deliberately from a script so changes are reviewable.
- Chezmoi is a poor fit for code with tests and history; use it (with `age` encryption or a
  secrets manager template) only for `config.yaml` if you want it replicated across machines.

- [x] `clara health [--since 24h]` (IPC `health`); `expect` added to mail triage, mail

## Risks

- Receipts rot if scripts stop reporting. Mitigation: mechanical fallback plus a health note
  "no receipt from a script that usually reports one".
- Alert fatigue. Mitigation: one daily digest; immediate pings only for failing/silent; tune
  `expect` rather than add rules.
- Stored events may contain sensitive content (mail, Webex). Trim and redact event data;
  keep the audit DB local and out of any synced directory.
